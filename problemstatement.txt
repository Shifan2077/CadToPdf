# ARECON — Phase 1: Multi-File CAD Project Ingestion Foundation

We are evolving the existing ARECON application from a single-DXF analyzer into a project-level CAD intelligence system.

The application currently:

* accepts DXF files
* parses CAD entities using ezdxf
* extracts dimensions
* performs drawing analysis
* displays analysis in the UI

The existing PDF-generation functionality is on hold for Phase 2. Do not activate or expose it.

The next goal is to build the foundation for a project containing hundreds of CAD drawings.

---

## 1. New Product Goal

The application should now treat a **project** as the primary unit rather than a single CAD file.

A project may contain:

* hundreds of CAD drawings
* multiple disciplines
* multiple drawing types
* multiple revisions
* schedules
* details
* plans
* elevations
* sections
* specifications
* alternative/tender options

The system must be able to ingest these files and preserve their extracted information independently while also associating them with a common project.

Conceptually:

```text
PROJECT
│
├── Drawing 001
├── Drawing 002
├── Drawing 003
├── ...
└── Drawing N
```

Do NOT implement cost comparison yet.

Do NOT implement final LLM reasoning yet.

Do NOT implement PDF generation.

This task is about creating the **data foundation**.

---

# 2. Core Principle

Separate the system into three levels:

```text
RAW
 ↓
what the CAD file literally contains

NORMALIZED
 ↓
what the system interprets it to mean

CALCULATED
 ↓
quantities/costs derived mathematically
```

For this task, primarily implement the **RAW layer**.

Do not overwrite raw extracted information with interpretations.

---

# 3. Project Data Model

Create a project model.

Conceptually:

```python
Project
    id
    name
    created_at
    updated_at
    drawings
```

Each drawing should have:

```python
Drawing
    id
    project_id
    filename
    file_type
    file_size
    upload_time
    status
    metadata
    extraction_summary
```

Do not force a drawing type yet.

Fields such as:

```text
discipline
drawing_type
floor
revision
```

should be nullable/optional because those will be determined later.

---

# 4. Raw CAD Representation

Each CAD drawing should preserve information such as:

```text

units
layers
blocks
layouts
model space
paper space
entities
dimensions

MTEXT

attributes
hatches
insertions

```

Use normalized Python data models rather than passing raw ezdxf objects throughout the application.

# 5. Entity Schema

Build a flexible base entity structure.

Example:

```python
CadEntity:
    id
    entity_type
    layer
    geometry
    bbox
    properties
    source_handle
```

The `properties` field should allow entity-specific information without forcing every entity type into a giant rigid schema.

For example:

```json
{
  "id": "entity_102",
  "entity_type": "LINE",
  "layer": "A-WALL",
  "geometry": {
    "start": [100.0, 200.0],
    "end": [500.0, 200.0]
  },
  "bbox": [100.0, 200.0, 500.0, 200.0],
  "properties": {
    "length": 400.0
  }
}
```

Preserve the original entity handle if available.

# 7. Preserve Raw Values

This is extremely important.

If the CAD says:

```text
1200 X 2100
```

store the raw value:

```text
"1200 X 2100"
```

Do not immediately replace it with:

```text
width = 1200
height = 2100
```

You may additionally provide parsed values, but preserve:

```text
raw_text
parsed_value
```

Likewise:

```text
"46MM THK."
```

should remain available exactly as extracted.

The raw data will later be used by normalization/LLM components.

# 10. Processing Status

Each uploaded drawing should have a processing status:

```text

```

The UI should show the status.

Example:


A failed file should not prevent the remaining files from processing.

# 20. Important: Keep Extraction and Interpretation Separate

Do not add code such as:

```python
if "D5" in text:
    category = "door"
```

as the primary semantic architecture.

Raw extraction should simply preserve:

```text
"D5"
```

along with source location and context.

Later, the normalization/LLM layer can interpret it.

Likewise, do not assume:

```text
A-WALL = wall
```

inside the raw extraction layer.

Store:

```text
layer = A-WALL
```

and let a later semantic layer decide what it means.

---

# 21. Source Traceability

Every extracted fact should be traceable back to:

```text
project
drawing
entity
CAD handle where possible
```

For example:

```json
{
  "fact": "1200 X 2100",
  "source": {
    "drawing_id": "drawing_002",
    "entity_id": "entity_881",
    "entity_type": "TEXT"
  }
}
```

This will later be critical when the LLM explains a cost or specification.


## Database Setup

Use **PostgreSQL running inside Docker** for the project database.

Do NOT require PostgreSQL to be installed directly on the host machine.

Create a `docker-compose.yml` at the project root that starts a PostgreSQL container.

Example architecture:

```text
ARECON
├── backend/
├── frontend/
├── docker-compose.yml
├── .env
└── ...
```

The Docker Compose configuration should:

* Use an official PostgreSQL image.
* Create a PostgreSQL database for ARECON.
* Configure username, password, database name, and port through environment variables.
* Persist PostgreSQL data using a named Docker volume.
* Expose PostgreSQL to the backend through the Docker network.
* Allow the backend running on the host machine to connect to PostgreSQL during local development.
* Include a health check so the backend/database dependency can be diagnosed easily.

Example environment configuration:

```env
POSTGRES_DB=arecon
POSTGRES_USER=arecon
POSTGRES_PASSWORD=1234566
POSTGRES_PORT=5432

DATABASE_URL=postgresql://arecon:1234566@localhost:5432/arecon
```

Do not hardcode production credentials in source code.

The application should be able to start the database with:

```bash
docker compose up -d
```

and stop it with:

```bash
docker compose down
```

Do NOT use `docker compose down -v` during normal development because the named database volume must preserve the project's data.

The backend must connect to this PostgreSQL instance using the configured `DATABASE_URL`.

Also add clear setup instructions to `README.md` explaining:

1. Docker must be installed and running.
2. How to configure `.env`.
3. How to start PostgreSQL.
4. How to start the FastAPI backend.
5. How to start the React frontend.
6. How to verify that PostgreSQL is running.

The database must be part of the actual implementation, not just an architectural placeholder.
